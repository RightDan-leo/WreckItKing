## 1. 两个版本怎么拆

表里 ID 11 的批注写「和 ID 18 的镜头展示巨龙方案冲突，可以做成第二个方案对比试下」。核实代码之后，冲突比批注写的更深。

### 1.1 冲突的实质

不是镜头高度之争，是**信息披露方向相反**：

- **方案 A（ID 18）**：开局就把终点摆给玩家看——你要打的是那条龙。**减少未知，换取目标感。**
- **方案 B（ID 11）**：把近处的威胁藏起来——挖开才知道后面有怪。**增加未知，换取惊吓感。**

两者在实现上也互相拆台：A 要长视距（封印环在 r=45.2，得看得见），B 要压低镜头并把矿墙做实（看不见就是目的）。压到能挡视线的高度之后，A 那个「目标一直在视野里」的后续收益就没了。

### 1.2 当前状态（两条都得从零做）

**A 侧**：游戏**没有任何开场运镜**。`init()` 建完场直接 `animate()`，t=0 就是普通跟随镜头。更关键的是——**巨龙在 t=0 根本不存在**，`finale.dragon` 初始为 `null`，只在 `startFlameDragonIntro()` L8847 才 `createFlameDragon()`。封印矿层不透明度 0.94，无金币、无宝石、无守卫，现在镜头摇过去只能看到一堵深青色实心墙。

**B 侧**：守卫透过矿墙可见是**刻意做的**。`frozen-ore-monsters.spec.md` 记着推导：矿墙径向 4~5 层、每层 opacity 0.46，叠起来透光不到一成，剪影怎么调都看不见，所以改成 `depthTest: false` 压在矿墙之上画（`setGuardXray` L7350，距离门控 `CONFIG.guardXrayRange` 16m），还专门调了眼距、暖白眼色。B 等于把这套整个推翻。

### 1.3 拆分方式：一份母版，三个投放子目录

**A 和 B 的唯一区别就是「前期镜头」和「能不能看到怪」。** 其余 11 条改动全部进**共同基线**，各版逐位一致——否则对比会被无关变量污染。这条是硬约束，实施时每合入一项都要确认它落在基线里而不是某一版里。

#### 部署形态（2026-09-08 定，已落地）

三版各自一条独立链接，测试者看不出还有别的版本、也无法互相切换——参数式（`?reveal=`）做不到这一点，一眼就能看出来还能改。

| 版本 | 地址 |
|---|---|
| A | `https://rightdan-leo.github.io/WreckItKing/a/` |
| B | `https://rightdan-leo.github.io/WreckItKing/b/` |
| C | `https://rightdan-leo.github.io/WreckItKing/c/` |

GitHub **一个仓库只有一个 Pages 站点**，所以「三个 Pages」实际是同一站点下的三个子目录。要真正独立的三个站点得开三个仓库，代价是三份代码人工同步、「共同基线逐位一致」这条验收变成真实风险——不值得。

#### 母版与产物

源码只有 `WreckItKing.html` 一份。`npm run build`（`build-versions.mjs`）把它生成成 `a/index.html`、`b/index.html`、`c/index.html`，每份做两处替换：

1. `const BUILD_VERSION = null;` → 写死成 `"a"` / `"b"` / `"c"`（母版 L788 附近）
2. `src="vendor/` → `src="../vendor/`，共 2 处。**子目录方案的关键坑**：母版在根目录、`vendor/` 与它同级，副本进了子目录就得退一层

**每一处替换都是硬断言，且产物要反向再验一遍。** 母版结构一变就整个构建失败，而不是静默产出三份内容相同的包——那种包发出去了根本看不出来，是这套管线最危险的失效模式。

运行时靠 `VERSION`（母版 L789）读版本，优先级是「写死的 `BUILD_VERSION` > `?v=` 参数 > 默认 a」。根目录那份 `WreckItKing.html` 保持 `BUILD_VERSION = null`，供本地开发和临时对照用 `?v=b` 切换。

`__wik.version()` 返回 `{ version, baked, lang }`，用来确认线上加载的到底是哪一版；**线上 `baked` 必须为 true**。

根 `index.html` 是三版入口页，不再直接跳转到母版。`?lang=en` 在子目录下照常工作（`a/?lang=en`，已验）。

### 1.4 C 版：狭窄营地与区块扩城（重新设计）

### 1.5 方案 A 的实施要点

复用终局那套演出机器：`startCinematic(steps)` L9049 / `updateCinematic` L9063 / `cinematicShot` L8757 / `framingDistance` L8748。

四个必须注意的点：

1. **`endCinematic()` L9073 定义了但全文件从未被调用。** 终局之后本来就不需要交还控制权，开场必须交还。不接这一步，开场放完玩家就永久锁死（输入门控是 `interactive = !cinematic.active && !ctaOpen` L11390）。

4. **时长是硬约束。** playable 的首次可交互时间直接决定流失。整局才 113~124 秒，开场占 4 秒就是 3.5%。建议**上限 3.5 秒，且任意触摸立即跳过**。

### 1.6 方案 B 的实施要点

| 旋钮 | 现值 | 目标 | 位置 |

## 2. 共同基线：11 条改动

按「风险从低到高 + 依赖顺序」分四批。

### 第一批：bug 与纯增量（不改数值、不动节奏）

#### ID 14 · 怪穿过没挖穿的矿山（bug）

**根因已定位。** `constrainEnemy()` L7550-7557 只钳巡游怪，守卫完全不做矿墙碰撞：

```javascript
// 只钳游荡怪。守卫是从矿墙内部出土的，它的家就在墙体半径上，一起钳的话
// 通道稍窄就会把它顶出扇区、或者干脆卡死在自己出生的那一格里。
if (enemy.userData.type === "rover") {
    resolveOreWallPosition(enemy.position, ROVER_BODY_RADIUS);
}
```

守卫的追击 L7763 和冲锋 dash L7727 都不过 `resolveOreWallPosition`。注释里说明了当初为什么不钳——怕守卫卡死在自己的出生格里。

**改法**：给守卫加**带出生豁免的**矿墙碰撞。记下守卫出土时所在的柱，只对「不是出生柱且 `blockCount > 0`」的柱做推离。另外 `updateRoverPatrol` L7121 直接写极坐标、不过 `constrainEnemy`，巡逻段也要补一次。

**验收**：`__wik.solidDepth(怪的 x, z)` 全程为 0；构造一局在没凿穿的墙两侧对峙，怪不得穿过来。

#### ID 4 · 弓箭没有攻击范围显示

当前射程（`playerAttackRange()` L5133 = `CONFIG.attackRange` 4.8 + `WEAPON_LEVELS[].reach`）：

| 等级 | reach | 攻击距离 | 自动索敌上限（+1.4 容差） |
|---|---|---|---|
| Lv1 镐头 | -3 | 1.8 | 3.2 |
| Lv2 弓 | +0.6 | 5.4 | 6.8 |
| Lv3 弓 | +0.6 | 5.4 | 6.8 |

现在**没有任何**攻击范围的地面指示。

**改法**：在 `playerRing`（L3607，玩家脚下已有的装饰环）旁边加一个 `attackRangeRing`，半径取**自动索敌上限**而不是攻击距离——决定「这一箭有没有」的是索敌那个数。仅在 `weaponLevel >= 2`（拿到弓）后显示。

**要注意**：别在挖矿时也一直亮着，画面会糊。建议只在视野里有敌人时淡入。

**无 spec 冲突**——`bow-weapon-line.spec.md` 没要求过这个 UI。顺带修掉 L887 那条过时注释（写着「Lv1 读出来 6.2」，Lv1 改成 -3 之后是 3.2）。

#### ID 12 · 资源图标区分度

根因是两组撞车：

1. **HUD 配色撞**：钻石 `#5fe6ff` vs 初级宝石 `#dcefff`，都是冷色浅色。
2. **3D 造型撞**：钻石和宝石**都是 `OctahedronGeometry`**（L3192 / L3212），只靠颜色和出现场景区分。

**改法**：三种货币要在**形状**上就分开，不能只靠颜色（色弱玩家、小屏、压缩后的广告素材都会把颜色吃掉）。

- 金币：圆 + `$`（不动）
- 钻石：改**六边形**或加明显的棱面高光，脱离菱形家族
- 宝石：保留尖菱形，三档靠颜色 + 体积区分（已有）

**必须同步改的四处**（漏一处就会前后不一致）：CSS L88-375、`SHARD_GRADES` L1552、`createSharedAssets` L3180-3244（3D mesh）、`drawTile` L4809-4841（地贴图标）。地贴那处尤其重要——注释里写着它是「判断该攒哪种钱的唯一入口」。

`mining-shard-tiers.spec.md` L39 写钻石是「菱形」，改完要同步。

### 第二批：战斗手感

#### ID 3 · 完美闪避读不懂（表里写「可以移除」，实际走折中）

**当前实现**：`ARPG.perfectWindow` 0.22s / `stunDuration` 0.8s / `stunDamage` ×2 / `hitStop` 0.08s。唯一触发路径是 `updateHazards` L8061-8065，唯一奖励入口是 `triggerPerfectDodge()` L7990。

**为什么不按表里写的整套删。** `attackState === "stunned"` 全文件只有这一处设置，删掉会连带失去踉跄状态、×2 伤害窗口、时间微顿、冲击环和专用音效。而 `arpg-combat-overhaul.spec.md` 整章的目标就是「让躲避有好处」——收益归零之后，挨打的代价只剩 0.25s 攻击硬直，理性玩法会退回「站着不动一直输出」。同时 TTK 会上升，而守卫血量刚在 `power-spike-tuning` 里整体抬过一轮（3400/5800/13000），得连着回调。

**已定：走折中方案，不整套删。**

反馈原话是「完美闪避是什么机制，不是很清楚」——抱怨的是**读不懂**，不是要这个机制消失。而 spec 的音效审计里 `perfect` 触发计数是 **0**，说明它在真实玩法里几乎从不发生：玩家看不懂，是因为他根本没见过几次。

**具体改法**：

1. **玩家看得见的文案统一改成「闪避」。** 去掉「完美」和「破绽」两个说法——玩家要读懂的只有一件事：躲开了。
   - `showDamage(player.position, "完美闪避", ...)` L8002 → `"闪避"`
   - 英文词条 `EN["完美闪避"]: "PERFECT DODGE"` L872 → `"闪避": "DODGE"`
   - 调参面板标签 L1943「完美闪避窗口 秒」→「闪避窗口 秒」，同 L1941 那段 note
   - `updateShardHud` 附近 L10236 的注释写着「只有『狂暴』『完美闪避』会命中」查表，改文案时这条要跟着改，否则英文版会漏翻
   - CSS class `.damage.perfect`、`playSound("perfect")`、`ARPG.perfectWindow` 这些**内部标识符保留原名**（见 §3.3）
2. **保留机制本身**：怪物踉跄（`attackState = "stunned"`）、受伤 ×2、时间微顿、冲击环，一个都不动。躲避的收益必须留着，否则理性玩法会退回「站着不动一直输出」。
3. **把窗口放宽，让它真的会发生。** `ARPG.perfectWindow` 0.22 → 建议 **0.45** 起步，实测后定。

**第 3 点要保留判定前提，不能改成「结算时在区外就算」。** `arpg-combat-overhaul.spec.md` 记过：只判「结算时在区外」的话，站得远的人什么都没做也天天触发，奖励变噪音。所以仍然要求玩家**确实在危险区里待到过最后一刻**（`hazard.lastInsideAt`），只是把「最后一刻」的定义放宽。

**改完必须重测**：`__wik.duel()` 三档 TTK。窗口放宽会让 ×2 更常触发、TTK 下降，而守卫血量刚在 `power-spike-tuning` 里抬过一轮，可能要回调。

**同步改 spec**：`arpg-combat-overhaul.spec.md` 第二节整章按新命名与新窗口重写，并把那条悬空的验收「真人过一局确认完美闪避的窗口手感」结掉——这次玩测就是那一局，结论是读不懂。

#### ID 17 · 弱化低级走廊的两只巡游怪

`ROVER_LANES` 现值：

| lane | hp | damage | speed | 追击速度（×`ROVER_RANGE.chase` 2.4） |
|---|---|---|---|---|
| lane-low | 300 | 2 | 2.2 | 5.28 m/s |
| lane-mid | 900 | 4 | 2.5 | 6.0 |
| lane-high | 2200 | 7 | 2.8 | 6.72 |

反馈说的是「挖出怪物之后巡游怪一起围攻，要打好久」——问题在**叠加**：低级守卫 3400 血本来就是一场硬仗（`power-spike-tuning` 刚抬上去的，为的是让预警和狂暴来得及登场），再被两只 rover 咬着，节奏就塌了。

**改法**：低走廊 rover 血 300 → 150、伤害 2 → 1，并把追击速度倍率单独降到 1.6 左右（现在 5.28 m/s 比玩家的 9.4 慢不了太多，甩不掉）。

**注意与 `power-spike-tuning` 的张力**：反馈还提了「前期的攻击力也太低了」，而前期镐头近战（reach -3）是那一轮**刻意**做难的。这次只弱化 rover、不动镐头和守卫血量，先看单独这一项够不够。

`corridor-rovers.spec.md` 的定位本来就是「氛围杂兵，拦不住人」——弱化**符合**原设计，无冲突。

#### ID 5 · 怪物技能打到矿山上会破坏矿山

现在 `updateHazards` L8056 结算只调 `damagePlayer()`，完全不碰矿石。

**现成可复用**：`pulverizeOreAround(center, radius, tierId)` L9488 → `pulverizeColumn()` L9465。这条路**没有** `requiredPickaxe` / `hardness` 闸门，终局巨龙（L9422）和横扫（L11314）都在用。

**改法**：在 hazard 结算处，对预警覆盖区调一次 `pulverizeOreAround`，半径取预警半径的 0.6 倍左右。

**三个必须挡住的坑**：

1. **封印矿要豁免**。否则怪能帮玩家把终局的墙拆了。
2. **别意外凿穿导致提前 breach**。凿穿会触发 `revealOreMonster` 和进度推进，怪帮玩家开路等于跳关。建议只允许破坏**已暴露面的表层格**，不参与 `blockCount` 归零的那一下。
3. **经济口径：已定，金币和宝石都要掉。** 理由是玩家把怪引到矿墙前换来的收益，属于正向体验，不该没收。

   这条和 `pulverizeColumn` 现有的注释**不矛盾，反而是同一套推理的延伸**。那句「金币在这条路径上是不结算的」只针对横扫，理由写得很清楚：横扫另给固定赏金 `BALANCE.sweepBounty`，按格再算一遍会把整局经济翻倍。**怪拆矿没有任何赏金补偿**，所以这里必须按格结算，否则玩家白干。

   实施上因此**不能直接复用 `pulverizeColumn`**——它为横扫写死了「跳过金币」。要给它加一个「是否按格结算金币」的入参，横扫和巨龙传 false（保持现状），怪拆矿传 true。

   宝石这边没有新问题：横扫路径本来就无视锄头等级发宝石，怪拆矿照做只是一致，不是新开的口子。

   **要量的是总产出。** 这是一条全新的、玩家可以主动触发的金币来源，得确认它不会把城的四级价格冲垮。口径：加之前加之后各跑一局自动机，比 city-2/3/4 四个 mark 的时刻。

`frozen-ore-monsters` 的「守卫堵路、必须凿穿才通」是既有设计，这条改动**未被文档化过**，实施时要在那份 spec 里补一段。

#### ID 15 · 最后一波割草

**现状是场上真的没怪**（见 0.2）。而且现在 `spawnRovers()` L7088 只在 `createArena()` 里调一次，3 走廊 × 2 只 = **6 只**，无重生、无波次概念。

**改法**：加一个终局波次钩子，在 `petEvolved` 或高级矿破墙后，在玩家与封印墙之间的走廊里刷一批**低血高数量**的 rover（建议 10~12 只，血量取 lane-low 量级）。目标是让满配玩家（Lv3 弓 + 进化龙，溅射 r=3.4 / 55%）一路平推过去。

**`corridor-rovers.spec.md` 有一条验收是「通关时长不变」**——这批怪必须秒死，不能变成一堵墙。实测口径：加波次前后的总时长差控制在方差内（现在是 113~124 秒）。

### 第三批：经济与节奏（互相耦合，要一起调一起测）

#### ID 8 · 前期货币逐步解锁

两个层次，建议都做：

**(a) HUD 首次获得才显示。** 改 CSS L330、L352 那两条强制常显，在 `gainGems` L5520 / `takeShard` L6322 / `registerCoinPickup` L9899 加 reveal 标记。成本低、收益直接——玩家不会在第 0 秒被告知有三种钱。

**(b) 真正把第二种货币往后推。** 光藏 HUD 不解决「6.2 秒就挖到宝石」。建议低级矿的预埋宝石**改成城 Lv2 之后才生成**（或前 N 格不埋），让开局有一段**纯挖金币**的循环。

另外 **主城 Lv1 在 0.8 秒建成**（cost 10 = startCoins 10，等于白送）。建议把 `CONFIG.startCoins` 降到 4~6，让第一次建城之前必须真的挖几下。

**注意**：`progression-ladder-rework` 的严格交替和钻石单轨是**已定**决策，这条只动「货币首次出现的时刻」，不动阶梯顺序。

#### ID 9 · 孵化台改常驻免费

**现状**：城 Lv4 解锁、8 钻石、且必须 `carryingEgg` 才能付。物理巢（nest 建筑）其实城 Lv3 就已经可见了。

**这条是本批风险最高的。** 它直接冲撞两条已验收的设计：

- `progression-ladder-rework` §2.1「建造孵化台和升级弓箭不应该同时存在」，验收项是**实测单轨 0 秒重叠**。孵化改免费之后这条其实自动满足了——两者不再抢同一种钱，重叠的只剩「一个免费动作」和「一个花钱动作」，性质完全不同。那条验收要按新口径改写，不能照抄
- `forgeWindowOpen()` L5488 用 `Boolean(pet)` 当武器 Lv3 的开关——孵化提前 = 武器 Lv3 窗口提前。详见下面的连锁 (2)

**已定的改法**：孵化台改成**免费 + 城 Lv3 就常驻**，并**保留「手动跑去捡蛋、抱回来放下」这个动作**——不是走到台子上就自动孵。

- 捡蛋那趟三十米的路是这条链上唯一的「玩家自己做的决定」，删了就只剩一个自动播放的过场，反馈要的非线性也就没了
- 单轨不塌：钻石消费点还剩武器线那两级，孵化不再占钻石
- 玩家可以自己决定「先跑去捡蛋」还是「先在城里升武器/锄头」

##### 省下的 8 钻：不并到任何地方，就让它富余

§0.4 的实测给了答案。**钻石全局唯一的堵点是进化台，等 15.2 秒**——玩家刚花 12 钻买完武器 Lv3，钱包见底，紧接着要为 14 钻的进化再刷一轮，而这一轮正好卡在终局之前。孵化台省下的 8 颗如果并进武器 Lv3 或进化，等于把这个 15.2 秒**原封不动保留下来**，那这条反馈就白改了。

所以：**孵化 8 → 0，其余价格一律不动。** 支出从 38 降到 30，供给仍是 44。

代价与核算：

- **富余会从 6 颗涨到约 14 颗。** 钻石没有第二个消费口，富余不会溢出到别处，只是终局钱包好看一点。`progression-ladder-rework` 本来就把富余当安全垫写进去过（钻石离散且有限，差一颗就是死锁）
- **要盯的副作用是双爆点会靠近。** `power-spike-tuning` 特意把武器 Lv3 从 6 抬到 12，就是要在「孵化」和「武器 Lv3」之间塞进一场高级守卫战。按实测速率（14 钻 / 15.2 秒 ≈ 1.1 秒每钻），多出的 8 钻约等于提前 9 秒，当前 74.2s 孵化 → 94.3s 武器 Lv3 的 **20 秒间隔会缩到约 11 秒**。仍然分得开，但要实测确认
- **改完重测 §0.4 这张表。** 若进化的等待仍然 >8 秒，再考虑把 `evolveCost` 从 14 降到 10——但这一步等数据，不预先定

##### 两个必须一起处理的连锁

**(1) 引导箭头会失控。** `getGuideGoal()` L10397 现在靠 `hatcheryZone.visible`（L10403）决定要不要指蛋，常驻之后这条门失效，箭头会在开局就把玩家往三十米外带——`progression-ladder-rework` 记过这个死锁：整局卡在中级矿墙前。新的优先级要保证**城 Lv3 之前箭头绝不指蛋**，之后也只在城里没有可付的地贴时才指。

**(2) 武器 Lv3 的窗口会跟着孵化时间一起滑。** 这条是查代码时才发现的，比引导那条更麻烦。`forgeWindowOpen()` L5488 拿 `Boolean(pet)` 当武器 Lv3 的开关，也就是**孵化早 = 武器 Lv3 早**。现在孵化落在 74.2 秒，是被「城 Lv4（100 金币）→ 8 钻石」两道门顶到那儿的；两道门一起拆掉之后，玩家理论上城 Lv3 一到就能去捡蛋，孵化可能提前到 40 秒上下。宠物是一个持续输出源，提前三十多秒会同时改掉中期 TTK 曲线和武器 Lv3 的出现时机——`power-spike-tuning` 刚把这两个爆点掰开，会被一次推回去。

处理办法：**把 `forgeWindowOpen()` 从 `Boolean(pet)` 改成看城 Lv4**。窗口就不再跟着孵化滑，宠物早到只是「玩家自己选了先去捡蛋」，这正是这条反馈要的。

**常驻门槛已定为城 Lv3**（物理巢那时候本来就已经看得见了，非线性最足）。宠物本身提前带来的难度变化没法靠读代码判断，**必须实测**：改完跑自动机，看宠物实际几秒到、总时长和三档 TTK 怎么变。曲线要是塌了，用调守卫血量来兜，不再往后挪门槛。

顺带记一笔：`completeCityUpgrade` L5233 有一句 `cityGate = gated && unlock !== "hatchery" ? unlock : null`，孵化台被特意排除在门之外，理由是「它是最后一级城解锁的，后面没有城了」。孵化台前移之后这句注释就过时了，要跟着改。

#### ID 16 · 金币 X5

**强烈建议走视觉方案，不动经济。** 理由：改经济要连带动 `CITY_STAGES` 四级价格、`sealOffering.cost` 120、`sweepBounty`、`startCoins`、rover/守卫掉落，还会推翻 `progression-ladder-rework` 里刚调平的低级矿消耗率——为了一个纯观感问题，代价太大。

**现成机制**：影子金币 `ghostRatio` 已经存在，横扫在用（`BALANCE.coinToss.sweep.ghostRatio` 2.5，18 赏金炸出约 63 枚视觉）。影子币不进账（`coin.ghost` 判定在 L9882），飞到背上就消失。

**改法**：给挖矿的两处 `dropCoins` 调用（L6521、L6540）加 `ghostRatio: 4`，新增 `BALANCE.coinToss.mine`。**入账逻辑一行不动。**

**要提前解决的上限问题**：`CONFIG.maxCoinDrops` 是 **110**，超出的部分**静默入账**（L9763）——玩家看不到那些币飞。5 倍影子币会让常态就顶到上限，反而把真实币挤成隐形。需要抬高上限并在移动端实测帧率（`coin-auto-collect.spec.md` 记着横扫峰值已经顶满 110，移动端待测）。

#### ID 13 · 初期场景太空旷

**先看清数字**：城 Lv4 外缘 14.6，自由圆 16.3（= 低级矿内缘），只差 **1.7 米**。所以「空旷」是**开局问题**——城 Lv1 半径才 6.6，外面是 9.7 米的空地。

**不建议动半径。** 自由圆 16.3 等于低级矿内边是结构性的（`radial-ore-field` 的可行走区定义），牵一发要连着改扇形侧壁 18.4、围墙 18.7、`guideThroughGate` 谷口 15.5、蛋的固定点 32.45、`SEAL_OFFER_RADIUS` 41.8 和整个终局构图。

**已定：廉价版先做，扩建版也要试，但要用安全的方式试。**

##### 13-a 廉价版（先做，进共同基线）

那 9.7 米空地上摆**待清理的碎石/废墟**，随主城每一级扩张被清掉、换成城区地面。视觉上就是「在狭小空间里一点点扩出去」，而**一个半径都不用改**。装饰摆位要避开 `CITY_CLEAR` 那个 T 形可行走区（L2228）和地贴槽位。

这部分零风险，和其余基线一起合。

##### 13-b 区块扩城（旧增量方案废弃）

原方案限制不改几何、通行半径和成长时刻，导致只能铺地加装饰。用户要求改成真实区块扩城，故由 [C 区块方案](c-block-expansion.spec.md) 全面取代。新验收包括出生压缩、前沿门迁移、建筑与设施落位、真实可走空间变化和逐块解锁，不再使用旧 A/C marks 相等作为 C 的合格判据。

### 第四、五、六批

见第 1 节与 §4 的排期表。**A/B 必须等前三批合入并稳定之后再开**，否则对比会被无关改动污染；13-b 与 A/B 可以并行（互不接触同一处代码），最后统一做 C 版判定。
