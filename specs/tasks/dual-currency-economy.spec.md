# Task: 双货币经济与双版本并存

> **对比已经做完，A 版（纯金币）于 2026-09-07 删除。** 结论是三货币版手感明显更好，代码里 `ECONOMY_PRESETS.coin`、`setupEconomy()`、开局那个版本切换按钮、`body.econ-gem` 那套 CSS 门控全部移除，`ECON` 直接常量指向唯一的预设。`?econ=coin` 这类老链接会静默落到三货币版。
>
> 本文件从此是**历史记录**：它记的是「为什么要拆货币、拆完撞到什么」这条推导，那部分仍然有效，也是这份文件现在的全部价值。下面这些结论已被后续推翻，各自就地标注：「锄头收钻石」「进化收金币」「高级守卫不掉钻石」「钻石地贴一次付清」四条见 [mining-shard-tiers](mining-shard-tiers.spec.md)；「双版本并存」「A 版必须逐帧等价」两条随本次删除作废。

## 目标

同时保留两套经济，可在开局切换，用来对比手感：

- **A 版（`coin`，现状）**：只有金币，四种消费共用一个池子。**行为必须和今天完全一致**，是对照组。
- **B 版（`gem`，新增）**：金币管建造，钻石管战力。钻石只从守卫身上掉。（现已扩为金币建造 / 宝石锄头 / 钻石宠物）

## 诊断：战斗不是回报低，是没有量

改之前先算清楚「没动力打怪」到底是什么问题。玩家伤害 `235 + (锄头等级-1)×190 + (进化 ? 220 : 0)`，每第三击 ×3.35，间隔 0.5 秒；挖矿 `round(威力/硬度)` 格每 0.3 秒，按 `cellsPerCoin` 折金币：

| | 打怪 | 挖矿 | 倍率 |
|---|---|---|---|
| 低级圈 | 5.9 金币/秒 | 2.4 金币/秒 | 2.4× |
| 中级圈 | 5.1 金币/秒 | 3.5 金币/秒 | 1.5× |
| 高级圈 | 7.3 金币/秒 | 4.7 金币/秒 | 1.6× |

**打怪一直是全场效率最高的动作。**问题不在单位回报，在于总量：全局只有 7 只守卫（低 2 / 中 2 / 高 3，每段矿墙一只），全打完也只有 15.8 秒战斗，占 170 秒流程的 9%，还没算宠物帮忙输出。十几秒撞一次的东西构不成循环，自然谈不上动力。

**而且每条本该依赖战斗的路径都有旁路**，现在可以近乎零战斗通关：

- 横扫的 `sweepKillGuard()` 会替玩家杀掉低阶守卫
- 龙蛋本来设计成中级以上守卫掉落（`maybeDropEgg`），但 `ensureEggAvailability()` 是无条件兜底——那段注释自己写着正常掉落路径「几乎必然错过」

所以钻石要解决的不是「打怪不划算」，是**把战斗从可跳过变成承重结构**。

承重靠的是货币本身：锄头只收钻石，钻石只从守卫身上掉。这条约束一旦立住，再往上加物理阻拦就是多余的了（见「供给的确定性」）。

## 为什么按「建造 / 战力」切，而不是「主城 / 锄头」

原始想法是钻石只用于锄头。改成按用途切，四项消费正好五五开：

| 货币 | 来源 | 消费 | 合计（现价） |
|---|---|---|---|
| 金币 | 挖矿 | 主城 ×4 + 孵化台 | 205 + 45 = **250** |
| 钻石 | 守卫 | 锄头 ×2 + 宠物进化 | 110 + 140 = **250** |

这样 **7 只守卫全部变成承重结构**，没有一只是白给的；主题上也立得住：金子盖楼，钻石变强。如果钻石只管锄头，三只高级守卫仍然毫无意义。

### 后来把进化改回了金币

上面这张表在实机试玩后被推翻了一半。进化那道钻石门是**多余的一道手续**：

- 锄头的钻石门有意义，因为锄头等级是「能不能凿开下一层矿」的硬门槛，卡在那儿玩家立刻知道要去打谁。
- 进化是整条流程的最后一步，此时锄头已经满级、高级矿也已经凿穿。再要求玩家回头把高级守卫清干净，玩家感受到的不是「变强要付出代价」，而是「还差一步却被拦下来」。

所以 `evolveCost` 回到 **140 金币**，`evolveCurrency` 回到 `coin`。连带的必然结果：**高级守卫不再掉钻石**——那时锄头已满级，钻石掉了也没处花，掉了等于白掉。它们改掉金币，正好喂进化这 140 的开销。

> **后续已推翻**：见 [mining-shard-tiers](mining-shard-tiers.spec.md)。加入第三种货币「宝石」后锄头改收宝石，钻石整体从战力线挪到宠物线（孵化台 + 进化），高级守卫也重新开始掉钻石。当时撤掉进化钻石门的理由——「结尾插一道让人卡住的门」——现在由引导和兜底承担，而不是靠把门拆掉。本节以下的价格与掉落表都只对**双货币阶段**有效，B 版的当前口径以 mining-shard-tiers 为准。

代价是高级档的两只守卫从「承重」退回「顺路」，钻石只覆盖锄头这一条线（5 + 8 = 13 颗）。这是明知的取舍：宁可让高级守卫的动机弱一点，也不要在结尾插一道让人卡住的门。守卫堵路那条规则仍然对高级矿生效，所以想凿穿高级矿墙还是得打，只是打完给的是金币。

顺带一个没预料到的收益：现在四项消费抢同一个池子，为了防止玩家揣着二级锄头站在高级矿墙前，`isZonePayable()` 里硬写了一套城↔锄头交替的人工锁。**货币一拆，推进顺序由收入来源天然决定**，那把人工锁在 B 版里可以关掉。

## 供给实测：天然流程刚好够用

钻石供给是这套方案唯一的真实风险——金币来自矿体是连续的，钻石是 7 次离散掉落，差一颗就卡住。这个数无法靠读代码推出来（取决于引导把人带到哪一段、横扫替玩家杀几只），只能实测。

`__wik.guards()` 跑满一局（A 版数值，横扫开启）：

| 时间 | 事件 | 累计击杀 低/中/高 |
|---|---|---|
| 5.5s | 低级守卫 1 | 1/0/0 |
| 26.4s | 低级守卫 2 | **2/0/0** |
| ~30s | 买二级锄头 | 余量 3.6 秒 |
| 40.3s | 中级守卫 1 | 2/1/0 |
| 68.9s | 孵化 | |
| 76.5s | 中级守卫 2 | **2/2/0** |
| ~94.5s | 买三级锄头 | 余量 18 秒 |
| 107.7s | 高级守卫 1 | 2/2/1 |
| 136s | 高级守卫 2 | **2/2/2** |
| 162.2s | 宠物进化 | 余量 26 秒 |
| 172.1s | CTA | |

**每一档采购之前，那一档的守卫刚好都死了。**而且这些都是玩家自己打死的，不是横扫代劳——横扫在 `completePickaxe()` 之后才 `defer(1.5, spawnSweepCharge)`，采购那一刻它还没响。

第三只高级守卫全程没被打，是高级档的天然冗余。

## 钻石数值

按实测供给反推，取小而好读的数：

| 档位 | 单只掉落 | 该档总供给 | 消费 | 结余 |
|---|---|---|---|---|
| 低级守卫 ×2 | 3 | 6 | 二级锄头 **5** | 1 |
| 中级守卫 ×2 | 4 | 8（+1 结余 = 9） | 三级锄头 **8** | 1 |
| 高级守卫 ×2 | —（改掉金币） | — | — | 1 |

每档留 1 颗富余，够吸收误差，但**不足以跳过任何一只守卫**（少打一只低级守卫只有 3 颗，买不起 5 颗的锄头）。

高级档那行原本是 6 颗 ×2 供宠物进化，进化改回金币后整行作废（理由见上一节）。钻石的全部流水因此收敛成：**赚 14，花 13，剩 1**。

数字保持在个位数很重要：钻石要读起来「贵重」，一旦做到几百就和金币没有区别了。

## 供给的确定性：从「堵路」改成「引导」

上面那张表是**引导驱动的 bot** 跑出来的。真人可能只挖一段就想走，于是供给的确定性需要一个保证，而不是靠概率。这里前后试了两版。

### 第一版（已撤）：守卫堵路

规则是「守卫出土后只要还活着，它那一段矿就凿不动」。守卫本来就冻在矿墙正中，凿穿的瞬间正好堵在隧道口，画面上早就是个路障。判据取「已出土 且 存活」而不是「存在」——冻着的时候得能挖，否则没法凿穿去唤醒它。也不会死锁：守卫不回血，玩家伤害必然打得死。

这条规则单独就能让战斗变成强制，零新增 UI，实测也确实有效（守卫活着时对该段发起 500 次开采，一格都没掉）。

**但它在手上读成一堵没道理的墙。**玩家想挖矿，游戏拦住他，理由是十几米外站着一只他还没注意到的怪。强制是达到了，动机没有——他不是「想去打怪」，是「被拦下来只好去打怪」。而且这堵墙出现的时机最糟：刚凿穿一段、正要往下挖的那一下。

### 第二版（当前）：门槛不动，把信息给足

钻石门槛本身已经是硬约束——锄头只收钻石，不打怪就升不了锄头，升不了锄头就凿不开下一层。玩家真正缺的不是阻力，是**「钻石从哪来」这条信息**。所以堵路撤掉，改由两件事承担：

- **地贴提示**：站上锄头地贴、钻石不够时报出还差几颗、去哪儿拿。这是玩家主动来问价的时刻，也是他最想知道答案的时刻。
- **箭头改指**：钻石不够且场上有活守卫时，引导指人不指矿。

两者要说同一件事。文案因此分两种：守卫已经跳出来了就说「打倒守卫就能拿到，箭头指着它」，把提示和箭头绑成一件事；还冻在矿里就说「凿开矿墙叫醒里面的守卫」，否则玩家会满地找一只根本还没出现的怪。

**提示要能反复说。**原先 `hintShown` 只在「这一帧能付款」时重置，于是钱不够的地贴一辈子只说一次话。这一版恰恰要它反复说：玩家踩上地贴发现买不起、去打了一只怪、钱还是不够，回来时最需要的就是再听一遍「还差几颗」。改成离开地贴就解锁。

实测下来 bot 一只守卫都没漏（低 2 / 中 2 / 高 2，和堵路版完全相同），而且**快了 8 秒**——省掉的正是「被墙拦住、绕去打怪、再回来」的那段折返。

`guardBlocksSegment` 这个开关保留在预设里，默认 `false`。它是调节奏时的备用杠杆，也是上面那段结论的对照组。`guardBlocking()` 和 `getGuideGoal()` 里对应的分支一并留着，翻回 `true` 就能复现第一版。

## 双版本怎么并存（已作废，2026-09-07 删除 A 版）

> 这一节记的是并存期的做法。对比结论出来之后 A 版整个删掉了，下面的预设表、切换方式、
> 「A 版必须逐帧等价」那条约束都不再成立。留着是因为「单文件 + 预设表」这个决定本身
> 是对的——它让两版对比只花了几天而不是几周，下次再要做 A/B 对照仍然应该这么切。

**不拆成两个 HTML 文件。**六千多行复制一份，之后每个 bug 都要修两遍，两版必然漂移，对比也就失去意义。

改为单文件 + 预设表：所有差异收进一个 `ECONOMY_PRESETS` 数据对象，代码里读的是预设字段而不是 `if (mode === 'gem')`，于是两版的差别是**数据差异，不是代码分支**。

```js
const ECONOMY_PRESETS = {
    coin: {
        label: "纯金币",
        gems: false,
        cost: { city: [10, 30, 65, 100], pickaxe: [25, 85], hatchery: 45, evolve: 140 },
        currency: { pickaxe: "coin", evolve: "coin" },
        guardGems: null,
        guardBlocksSegment: false,
        orderInterlock: true
    },
    gem: {
        label: "金币+钻石",
        gems: true,
        cost: { city: [10, 30, 65, 100], pickaxe: [5, 8], hatchery: 45, evolve: 140 },
        currency: { pickaxe: "gem", evolve: "coin" },
        guardGems: { low: 3, mid: 4 },   // 高级档不给：那时锄头已满级，钻石没处花
        guardBlocksSegment: false,       // 曾经是 true，见「供给的确定性」
        orderInterlock: false
    }
};
```

切换方式两条，都要有：

- **URL 参数** `?econ=gem`，缺省 `coin`。分享给同事时一条链接就是一版，不用教人怎么点。
- **开局界面上的小切换**，本地来回对比时不用改地址栏。上线时随调试钩子一起摘掉。

**A 版必须逐帧等价于今天。** 预设的 `coin` 分支要走和现在完全相同的代码路径，不能因为「顺手重构一下」让对照组变味。验收里有一条专门测这个。

## 实现中撞到的两个死局

两个都只在钻石版出现，根因相同：**金币的收入是连续的，钻石是离散且有限的**，所有「先欠着、早晚补上」的既有设计在钻石上都会变成硬卡死。

### 一、引导指矿，人却被按在凿不动的墙前面

第一次跑通 B 版时在 105.9 秒卡死，跑到 600 秒也没结束。现场：玩家站在 `high-0` 前 1.4 米，该段守卫**出土且存活**，`guide.speed` 为 0，`nearestTarget()` 有目标但敌人数量一直是 1。

原因是守卫堵路的粒度错配：**block 是按整段矿算的，而一段高级矿墙横跨约 15 米，守卫站在段中心。**玩家从段的一端靠过去时守卫在自动索敌范围（`attackRange + 1.4` = 5.8 米）之外，于是整段都凿不动、而堵路的那个东西在十米开外站着，玩家对着墙无限弹开。

修法：`getGuideGoal()` 里发现选中的矿段被守卫堵着时，**指人不指矿**。

堵路撤掉之后这个死局从根上不存在了（墙没了就不会把人按在墙前），但那条「指人不指矿」的判断被推广成了更宽的一条：**钻石不够就指人，不管墙堵不堵**，而且排在矿分支之前。原来那行代码留着，只在把 `guardBlocksSegment` 翻回 `true` 时才生效。

### 二、地贴收了一半钻石，把钻石锁死了

同一局里，玩家带着 7 颗钻石路过进化地贴，地贴照既有逻辑「站上去就自动扣钱」把 7 颗全收了，卡在 `evolve:7/12`。此时手上归零、场上剩下的高级守卫还冻在矿里没出土，`nearestLivingGuard()` 返回空——钻石既拿不回来也赚不到。

这就是 [pickaxe-upgrade-sweep](pickaxe-upgrade-sweep.spec.md) 里记的那条「地贴自动扣钱」长尾，在金币下只是绕远路，在钻石下直接是死局。

修法：**钻石地贴要么一次付清，要么一颗都不收**，并提示还差几颗、去哪儿拿。金币维持原样——分批付款那个进度条的手感值得保留，而且挖矿早晚补得上。

> **后续已推翻**：一次付清读起来像「没收到钱」——玩家站上去、有钻石、什么都没发生。改回了和金币一样的分批捐献，死局则由 `ensureProgressAffordable()` 认货币补齐来兜（它现在会按地贴真正要收的那一种货币补，钻石、宝石都认）。

### 三、兜底自己被顶住（后续，走廊巡游怪引入）

上面两条讲的是兜底**补什么**，这一条是它**什么时候该触发**。原来的守门条件是 `enemies.some(alive)`——场上还有怪，就认为玩家还有收入。加进走廊巡游怪之后这条假设在两个方向上都破了：那六只只掉金币，且其中两只待在玩家还没凿穿的走廊后面。

金币版实测跑满 500 秒没结束：玩家差 3 金币，兜底因为「场上还有两只怪」不肯补，而那两只他走不到。修法是让守门条件同时认**货币对不对口**和**怪够不够得着**，细节见 [corridor-rovers](corridor-rovers.spec.md) 的「死锁」一节。

这条对本 spec 的意义：三种货币产地互不重叠之后，任何「还有收入来源」的判断都不能再笼统地问「场上还有东西可打吗」，必须问「还有能产出**这一种**钱的东西吗」。

## 实测结果

| | A 版（纯金币） | B 版（进化收钻石） | B 版（进化改金币） | B 版（撤掉堵路，当前） |
|---|---|---|---|---|
| 通关时长 | 167.1 秒 | 133.9 秒 | 150.3 秒 | **142.3 / 142.6 / 142.8 秒** |
| 击杀守卫 | 低 2 / 中 2 / 高 2 | 低 2 / 中 2 / 高 2 | 低 2 / 中 2 / 高 2 | 低 2 / 中 2 / 高 2 |
| 钻石收支 | — | 赚 26、花 25、**余 1** | 赚 14、花 13、**余 1** | 赚 14、花 13、**余 1** |
| 报错 | 无 | 无 | 无 | 无 |

撤掉堵路后三轮跑下来只差 0.5 秒，节点也几乎重合
（`0.7 / 18.6~18.9 / 26.1~28 / 46.3~47.1 / 63.5~65.2 / 77.2~79 / 99.1~100.9 / 132.3~132.9 / 142.3~142.8`）。
**一只守卫都没漏**，说明「箭头指人 + 地贴报价」这套软引导达到了和硬墙一样的覆盖率。
快掉的 8 秒是省下来的折返：原先玩家被墙拦住时人已经贴在矿上了，得反身去找怪再走回来。

钻石流水与设计表**逐项吻合**：低级 2 只 ×3 = 6，花 5 剩 1；中级 2 只 ×4 = 8，累计 9，花 8 剩 1。锄头在 91 秒满级，此后钻石不再有消费。

进化改回金币后 B 版反而**长了 16 秒**（133.9 → 150.3）：那 140 的开销从「打两只高级守卫」换成了「挖够金币」，而挖矿是连续产出、比两次离散掉落慢。顺带把 A/B 的差距从 33 秒收窄到 17 秒（同批次 A 版复测 176.8 秒，差 26 秒），两版都落在 2–4 分钟带内。

A 版关键节点与改动前逐项对齐（`0.7 / 17.1 / 30 / 49.3 / 66.5 / 68.3 / 94.6 / 121 / 156.7 / 158.1 / 166.7`），前六个节点完全一致，后段差异落在既有的 166.7–172.1 秒抖动区间内。

守卫堵路（现已撤掉）当时确实是硬门槛而不只是提示：守卫活着时对该段发起 500 次开采，**一格都没掉**（102/126 保持不变）；守卫死后同样的调用把整段清空。

A 版复测 167.1 秒，节点 `0.7 / 17.1 / 30 / 49.5 / 66.5 / 68.4 / 95 / 121.4 / 157.1 / 158.5 / 167.1`，
与本文件记录的基线逐项对齐，本次改动没有碰到对照组的时序。唯一的行为变化是
**「轮不到」的提示现在也能反复触发**（`hintShown` 的重置条件放宽了）——只影响 toast，不影响任何数值或时序，
而且反复踩一张轮不到的地贴本来就该反复被告知原因。

## 两个环境坑

- **本地 dev server 会把 `WreckItKing.html?econ=gem` 重定向成 `/WreckItKing`，连查询串一起丢掉。**分享链接必须用不带 `.html` 的路径：`http://<host>/WreckItKing?econ=gem`。
- **`#ui` 整层是 `pointer-events: none` 的 HUD 罩子**，切换按钮不显式写 `pointer-events: auto` 的话点击会穿透到 canvas，那一下正好被当成「开始游戏」，版本永远切不了。

## 待解决：金币需求腰斩，节奏会明显变短

B 版把锄头（110）移出金币池后金币消费下降，而且掉钻石的守卫不再掉金币。**实测 142.5 秒对 167.1 秒，短了 25 秒**，比预估的腰斩轻得多——主要是进化那 140 又被放回了金币池。

（撤掉守卫堵路之前是 150.3 对 176.8，差 26 秒。撤掉后两版各自都短了一点，差距基本没变。）

已与用户约定**功能先做完，通关时长最后统一调**，所以本次不做补偿性回调，但要记下可用的杠杆：

1. **`guardKeepsCoins: true`**（预设里已经留好开关）。守卫同时掉金币和钻石，一行改动就能把那 102 金币收入加回来，击杀反馈也更厚。最省事，优先试这个。
2. **抬主城与孵化台价格**，把金币总需求拉回 500 附近。会改变各级城解锁的时间点，而 `unlock` 挂在城等级上，需要重测。
3. **调 `cellsPerCoin`**，直接降挖矿产出速率。

倾向先试 1，不够再叠 2。
