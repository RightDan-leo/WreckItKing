# Task: 矿层走廊巡游杂兵

## 目标

四道扇形矿墙之间夹着三条空走廊。它们原先是纯过道：玩家凿穿一层、穿过去、对着下一堵墙接着凿，中间那段路上什么都不发生，整个矿区看起来像一组静物。

在每条走廊里放两只来回踱步的杂兵。隔着半透明矿墙就能看见远处有东西在动，「外面还有一层」这件事不用箭头也读得出来。

**它们是氛围，不是内容。**验收的硬指标是通关时长不变——巡游怪不该改变节奏、经济或推进结构，加进去只为让这个世界看着是活的。

## 走廊几何

内外边界从 `ORE_TIERS` 现算（`laneGeometry()`），不写死。矿层的半径和厚度被终局构图反复调过——高级矿就为了给封印矿让位内移过一次——写死的话下次一调，怪就会站进墙里。

| 走廊 | 内侧矿墙 | 外侧矿墙 | 空隙 | 中线半径 | 中线弧长（90° 扇形） |
|------|----------|----------|------|----------|----------------------|
| lane-low | 低级矿 20.7 | 中级矿 24.9 | 4.2 | 22.8 | 35.8 |
| lane-mid | 中级矿 30.1 | 高级矿 34.8 | 4.7 | 32.45 | 51.0 |
| lane-high | 高级矿 40.2 | 封印矿 43.4 | 3.2 | 41.8 | 65.6 |

每条走廊两只。**布局按米算，不按弧度**（`ROVER_PATROLS` 的 `gap` / `spanArc`，除以走廊半径才换成角度）。

初版写的是弧度（巡逻中心 `SECTOR.center ± 0.35` rad，区间 `± 0.22` rad），三条走廊共用一组数。这是错的：弧长等于半径乘角度，同样的 0.35 弧度在最内圈是 8 米、在最外圈是 14.6 米，于是「两只怪离主路多远」在三条走廊里差了将近一倍。后果见下面「追击范围」一节——最外那条的怪永远碰不到人。

改按米之后两只不再左右对称：

| | `gap` | `spanArc` | 区间 | 离中轴最近 |
|---|---|---|---|---|
| 近侧那只 | +2.6 | 4.5 | -1.9 ~ +7.1 | 1.9（区间横跨中轴） |
| 侧翼那只 | -9.5 | 4.5 | -14 ~ -5 | 5 |

对称是要避免的：那样「两只怪与中轴等距」，任何 aggro 值都是同时扑上来或者同时不理人，没有中间状态。现在近侧那只离中轴最远也只有 7.1 米，过路必定惊动它；侧翼那只只有走到内侧那 4 米（约四成时间）才够得着中轴。遭遇强度于是跟着巡逻相位和走位变。

`spanArc` 要给扇区边界留余量，贴着边走会半个身子插进侧面岩壁。最紧的是最内圈（半宽 17.9 米）：侧翼那只走到外端是 14 米，留 3.9 米。实测 100 秒巡逻共 2400 次采样，`inBand` / `inSector` 零违规。

## 为什么必须和守卫分开

`type: "rover"`，不是 `"monster"`。这不是命名偏好，是三处硬依赖：

1. **`nearestLivingGuard()` 按 type 取人。**钻石不够时箭头要指向「能给钻石的那只怪」。游荡怪要是也算守卫，箭头就会指向一只根本不掉钻石的杂兵。
2. **`killEnemy()` 的掉落分档。**守卫掉钻石（`guardGems`），游荡怪只掉金币。
3. **`ensureProgressAffordable()` 判断收入来源。**见下面的死锁一节。

`nearestTarget()` 只看 `alive` 和 `attackable`，所以玩家和宠物照样会自动打它们——路过顺手清掉，这是想要的。

## 形态：三轮试错

固定俯视相机决定了一切。前两版都是可读性问题，不是审美问题。

| 版本 | 做法 | 失败原因 |
|------|------|----------|
| 1 | 身体用 `tier.chunkColor` | 那正是矿石碎块的颜色。凿穿一层后走廊里躺着几十块同色碎石，怪站在里面挑不出来 |
| 2 | 身体改深色（`0x39323f`） | 忘了这些怪站在地面上，而地面是 `0x151221` 的近黑紫。暗身体贴暗地面，俯视下整只怪只剩背上三根发光刺可见 |
| 3 | 骨灰白（`0x9a93a8`）+ 矿层辉光背刺 | 成 |

骨灰白是唯一同时避开这两头的：地面极暗所以它是清楚的亮剪影；低饱和所以不会被认成守卫（守卫穿的是饱和的绿 / 紫 / 橙红）。层级信息交给会发光的背刺和眼睛带——背刺取所在走廊内侧那层矿的 `glow`，读起来像是从那道墙里爬出来的东西。

形态上还有两处是为俯视角专门加的：

- **尾巴**（三节递减、向后上翘）。没有它，躯干加四条腿从上面看只是个带亮点的长方块，认不出哪头是头。
- **躯干宽度压到 1.2**（长 2.5）。1.5 宽配 2.5 长的俯视投影读出来是个方箱子。

`scale` 是按「站在走廊里能看出是只怪」定的，不是按强度：0.5 那一版本体只有 1.3 米高，比玩家矮一头。0.62 / 0.72 / 0.85 起玩家一眼能认出轮廓，同时还明显小于同层守卫（0.72 / 0.95 / 1.18，本体高出一米多）。

眼睛发光但**不关深度测试**。守卫那套 X 光是为了「隔着矿墙看得见」，游荡怪本来就站在空地上，再穿透就会连主城的房子一起穿过去。

## 行为

```
巡逻 ──玩家进 11 米──> 追击（复用 updateMonsterCombat，速度 × 2.4）
  ^                          │
  ├──── 玩家出 18 米 ────────┤
  └──── 或自己跑出走廊 3 米 ─┘
```

- **巡逻**沿走廊中线的圆弧来回踱步，走到区间端点掉头。角速度除以半径，否则外圈那条走廊上的怪会明显比内圈跑得快——三条走廊半径差了将近一倍。线速度取 `speed × 0.45`（约 1.0–1.26 m/s），是悠闲踱步而不是巡逻兵行军。
- **脱战后回到离当前位置最近的那个巡逻角**，省掉一段横穿走廊的直线折返。它是「在这条走廊上活动的东西」，不是「守着一个点的哨兵」。
- **迈腿动画**（对角腿同相）纯装饰，但没有它这些怪就是贴着地面平移的方块，「在走动」这件事全靠位置变化去猜。
- **攻击姿态**：守卫的蓄力是举起双臂，靠 `arms` 里那两个方块转出来；四足没有手臂，`arms` 是空数组，那个循环在它身上一圈都不跑。不补一手的话它挥击时整只怪一动不动，玩家只看到脚下亮起一个红圈、猜不出是谁要打他。改成整只身体前倾压低（`rotation.x`），读作低头猛扑。不能用 `position.y` 做下压——`updateEnemies` 每帧会把 y 拍回 0。

不参与玩家碰撞（`resolveCirclePosition` 只解 `solidColliders` 和矿墙），所以它们不会挡路，自动流程也不会被卡住。

### 追击范围：初版给小了，但根因不在范围上

初版是 `ROVER_AGGRO = 5` / `ROVER_LEASH = 9`，理由写的是「游荡怪的本职是在那儿动，贴脸了才还手；给到守卫那种 9–11 米，玩家一进走廊就会被两只怪同时黏上，过路变成清场」。

**这个顾虑是错的方向。**实测沿扇区中轴径向穿过三条走廊，一只怪都不会理他——`engagedPeak` 全是 0。它们退回成了纯布景，而放它们进来的全部理由就是「让世界看着在动」。

原因是上面「走廊几何」记的那个弧度 / 米的错：两只怪按弧度对称摆在扇区两侧，越外圈离主路越远。实测站在中轴上离最近那只的距离：

| 走廊 | 中线半径 | 离最近那只 |
|------|----------|-----------|
| lane-low | 22.8 | 7.7 |
| lane-mid | 32.45 | 10.7 |
| lane-high | 41.8 | 13.5 |

**先试过纯加大 aggro，结果印证了「单一数值兼顾不了」**：9 只救回低级那条（中、高实测仍是 0）；12 才够到最外那条的 13.5 米，而 12 又让内两条变成「进走廊必被两只同时黏上」（低级走廊两只间距 16 米，中点离两只各 8 米）——恰好是初版想避免的那个问题。

所以改的是分布而不是感知半径（见「走廊几何」的 `gap` / `spanArc`）。近侧那只离中轴最远 7.1 米之后，`aggro: 9` / `leash: 14` 就够了；leash 取 aggro 的一倍半，否则玩家往外退两步怪就转身回去踱步，刚打起来又断掉。

> 这组数是**第一轮**的结果，只解决了「会不会遭遇」。定版值见下一节（第二轮把速度和空间条件加进来之后是 `{ aggro: 11, leash: 18, chase: 2.4, tether: 3 }`）。

实测三条走廊各沿中轴取 17 个采样点：全部至少惊动一只（17/17），低、中两条峰值 1 只，高级那条采到 2 只（侧翼那只当时正停在区间内端 -5.03 米处，属巡逻相位，不是几何问题）。

**敢把一只放在主路上，是因为玩家速度 9.4 而它们只有 2.2 ~ 2.8**（`CONFIG.playerSpeed` 对 `ROVER_LANES[].speed`）。快三四倍意味着它拦不住人，只能擦一下——想打就停下打，不想打直接跑过去，不会变成每层一道必须清掉的关卡。这条也是「不挡路」那条约束在追击范围上的延伸。

顺带删掉了 rover `config` 里那份 `chaseRadius` / `reengageRadius`：守卫那套 `updateEnemyLeash` 是绕出生点拴绳的，没有 `homePosition` 就直接 `return false`，而 `homePosition` 只有守卫出土时才挂。那是一份永远不会被读到、又会在拖滑块后变陈旧的拷贝值。

### 追击范围（第二轮）：范围不是瓶颈，速度才是

上面那轮把「会不会遭遇」修好了，玩家反馈的下一个问题是「很容易就脱离战斗，没有威胁」。再调 `aggro` / `leash` 是没用的，因为瓶颈不在感知范围：

- 上一节末尾那句「快三四倍所以拦不住人」，反过来就是**它永远追不上人**。脱战完全由玩家单方面决定：从贴脸的 2.6 米跑到 `leash` 14 米只需要 `(14 − 2.6) / (9.4 − 2.8) = 1.7` 秒。实测 1.67 秒，和公式吻合。
- 接近阶段更糟：走廊宽 3.2 ~ 4.7 米，径向穿过去只要 0.45 秒，**比它 0.5 秒的前摇还短**——跑着过路的玩家连一次挥击都不会挨到。而它从九米外走过来要三四秒，那时候玩家早凿穿下一堵墙走了。

所以加的是 **`ROVER_RANGE.chase`（追击时的速度倍率，乘在 `ROVER_LANES[].speed` 上，巡逻不乘）**，见 `chaseSpeedOf()`。守卫不乘——它们是守着一段矿墙的门，本来就不该追出去。

**但光提速会把主城搭进去。**开阔地带（凿穿三层后）沿径向逃跑的实测：

| `chase` | 甩掉用时 | 甩掉时玩家半径 |
|---------|---------|--------------|
| 1（原速） | 1.87 s | 26.0 |
| 1.8 | 3.13 s | 14.1 |
| 2.4 | 4.20 s | 3.1 |
| 2.8 | 追到底（14 s 未脱战） | 1.5 |
| 3.2 | 追到底 | 2.5 |

矿区径向总共才四十米出头，所以 2.4 已经意味着「跑穿整个矿区才甩得掉」，2.8 以上是**一路跟进主城正中**。主城是安全区，也是玩家踩地贴做交互的地方（见 `city-layout` 那条约束），不能让走廊怪进去。

**换成空间条件解决**：`roverStrayed()` —— 怪自己的半径离开所属走廊超过 `ROVER_RANGE.tether` 米就放弃。于是两件事同时成立：走廊里可以追得很凶，而每条走廊的危险范围是明确的、玩家能学会的（退回自己凿开的隧道就安全）。读作「追到地盘边上就不追了」，比「跑够远它会忘记你」更容易看懂。

定版 **`{ aggro: 11, leash: 18, chase: 2.4, tether: 3 }`**。加了 tether 之后再测径向逃跑，三条走廊各自在自己的边界上准确放弃：

| 走廊 | 甩掉用时 | 怪追到的最内半径 | 边界（内沿 − tether） |
|------|---------|----------------|---------------------|
| lane-high | 2.33 s | 37.2 | 40.2 − 3 = 37.2 |
| lane-mid | 1.17 s | 27.1 | 30.1 − 3 = 27.1 |
| lane-low | 2.00 s | 17.6 | 20.7 − 3 = 17.7 |

整局跑下来怪离圆心最近 18.6 米（主城半径约 14），**进城采样 0 次**。

顺带修了迈腿动画：`animateRoverGait` 原先按 `moving` 布尔值用写死的频率 7。巡逻是 1.0 ~ 1.26 m/s，追击乘完是六七米每秒，同一个频率配这两档，追人时整只怪会贴着地面平移过来、腿在原地小摆，读作滑行而不是奔跑。改成传实际速度，频率按 **速度的平方根** 缩放（正比的话追击时频率要翻五倍以上，腿糊成一片）；参照速度取它自己的巡逻速度，所以巡逻观感和原来完全一致。

## 经济：掉落必须压住

初版给 4 / 8 / 14（合计 52 金币），相当于把守卫那 102 的击杀收入加厚一半。实测钻石版从 142.5 秒掉到 102.8 秒——**这些怪是氛围，不该动经济**。

压到 2 / 3 / 5（合计 20）之后它只剩「打死了有响」这一份作用，不足以让玩家改主意专门去刷。两版通关时长因此都回到基线的 1.3 秒之内（见实测结果）。

**只掉金币，一颗钻石都不掉。**钻石是守卫的专属产出，一局就那么十几颗、每一颗都对着一次采购；游荡怪有六只还会重复遭遇，掉钻石会把那套精算的供给冲垮，也会让玩家改去刷杂兵而不是打守卫——而守卫才是矿墙推进的那道门。宝石同理（它只埋在矿里）。

`config` 用 `Object.create(lane)` 挂原型，不拷字段。守卫那边 `config` 就是 `tier.monster` 本身，所以调参面板拖「伤害」「掉金币」是当场生效的；拷值的话这两根滑块会变成必须重载才见效，和面板上写的说明不符。血量另算——它被读成 `maxHp` 烘进对象，字段表里标了 `reload`。

## 死锁：兜底救济必须认「货币」和「可达」

`ensureProgressAffordable()` 是整条流程的最后一道防线，它要回答「玩家还有没有赚钱的路子」。原来的判断是 `enemies.some(alive)`——场上还有怪，就认为还有收入。加进六只游荡怪之后这条假设在两个方向上都破了。

### 一、货币不对口

三种货币的产地互不重叠：金币来自挖矿和大部分击杀，钻石只从守卫身上掉，宝石只埋在矿里、一颗都不从怪身上出。不分货币的话，走廊里那六只只掉金币的游荡怪会把钻石和宝石的兜底一直顶住——玩家守着一堆凿不动的矿、和一只给不了他要的那种钱的怪。

判断因此改成按 `blocking` 地贴收的货币分档：

| 缺口 | 什么算「还有收入」 |
|------|--------------------|
| 宝石 | 什么都不算（只能靠挖，函数开头那条「还有矿可挖」已经管了） |
| 钻石 | 只有掉钻石的守卫（`ECON.guardGems[tierId]`） |
| 金币 | 玩家走得到的游荡怪；守卫要看这一档有没有钻石可掉（`guardKeepsCoins`）——钻石版三档守卫全掉钻石，那一版里守卫完全不是金币来源 |

`blocking` 的计算因此要提到这个判断之前：不知道缺的是哪种货币，就没法判断谁算收入。

### 二、怪在玩家进不去的地方

**实测死锁**（金币版，把掉落调到 0 暴露出来）：玩家站在锄头地贴上差 3 金币，低中两层的怪都打完了，兜底却因为「场上还有两只怪」不肯补——而那两只是 `lane-high` 的，站在高级矿背后那条他还没凿穿的走廊里。引导又把他按在地贴上等一笔永远不会来的钱。跑满 500 秒都没结束。

`roverReachable()`：玩家能不能走到这只怪跟前，取决于它那条走廊的内侧矿墙凿穿了没有（`breachedByTier[lane.inner] > 0`）。这和「矿」那一侧的 `canMine()` 是同一类判断——`canMine` 查的是锄头等级，这里查的是墙破没破。

注意这个死锁在掉落 > 0 时也存在，只是概率低（游荡怪的金币恰好补上了缺口），所以修复不是为了那个测试用例。

## 终局清场

`startFlameDragonIntro()` 里移除所有还活着的游荡怪。破封那几个机位都架在走廊里，最高级那条走廊正是玩家站定对峙的地方——一只杂兵在画面里踱步、或者干脆扑上来挥两下，会把这段本该只有一件事发生的戏拆成两件。它们也没法在演出里被打，玩家的输入这会儿已经交给镜头了。

## 改动范围

| 位置 | 改动 |
|------|------|
| `ROVER_LANES` / `ROVER_PATROLS` / `ROVER_RANGE` | 新增配置。`ROVER_PATROLS` 按米（`gap` / `spanArc`）；`ROVER_RANGE` 取代原先的 `ROVER_AGGRO` / `ROVER_LEASH` 两个 const，为的是能进调参面板当场拖。第二轮加了 `chase`（追击速度倍率）和 `tether`（追出走廊多远放弃） |
| `laneGeometry()` | 新增：从 `ORE_TIERS` 算走廊内外边界与中线 |
| `createRover()` / `spawnRovers()` | 新增：四足模型与建场生成，挂在 `createOreField()` 末尾 |
| `updateRover()` / `updateRoverPatrol()` / `animateRoverGait()` | 新增：巡逻、脱战归位、迈腿。`animateRoverGait` 第三参数由 `moving` 布尔值改为实际速度（迈腿频率按速度平方根缩放，否则追击时是滑行） |
| `chaseSpeedOf()` | 新增：追击速度。游荡怪乘 `ROVER_RANGE.chase`，守卫按原速。被 `updateMonsterCombat` 的追击分支和迈腿动画共用 |
| `roverStrayed()` | 新增：空间脱战条件。怪自己的半径离开所属走廊超过 `tether` 就放弃，防止走廊怪一路跟进主城 |
| `ROVER_PATROL_PACE` / `PATROL_GAIT` | 新增常量。巡逻速度比例（原先散在 `updateRoverPatrol` 里的字面量 `0.45`）与巡逻迈腿频率，迈腿缩放以它们为参照 |
| `roverReachable()` | 新增：可达性判断，给兜底救济用 |
| `updateEnemies()` | rover 走自己的分支（不走 `updateEnemyLeash`） |
| `setMonsterPose()` / `resetMonsterPose()` | 补四足的前倾蓄力姿态 |
| `killEnemy()` | rover 分支：只掉金币 |
| `ensureProgressAffordable()` | 收入来源按货币分档 + 认可达性；`blocking` 计算提前 |
| `startFlameDragonIntro()` | 清掉存活的 rover |
| `TUNING_SCHEMA` / `tuningRoot()` | 新增「走廊巡游怪」分组（血量 / 掉落 / 伤害 / 追击范围 / 追击速度 / 走廊外拴绳 / 巡逻布局），`ROVER_LANES` / `ROVER_RANGE` / `ROVER_PATROLS` 进调参根。追击那几根即时生效，巡逻布局建场时烘进对象所以标 `reload` |
| `__wik.rovers()` | 新增调试钩子：所在走廊、半径是否落在空隙内、是否在扇区内、屏幕 NDC、脱战状态 |

## 实测结果

> 下面这组绝对秒数是**当时那一版**的基线对照，用途是「掉落值有没有动经济」。后续 ARPG 改造与钻石武器线又改过战斗时长和守卫掉落，当前口径见 `arpg-combat-overhaul.spec.md`。这张表要读的是三列之间的差，不是数值本身。

同一份代码，只改掉落值，`__wik.auto()` 全自动跑到结局：

| | 无巡游怪 | 掉落 = 0 | 掉落 = 2/3/5（定版） |
|---|---|---|---|
| 金币版 | 159.3 秒 | 死锁（修复前）→ 164 秒 | **158 秒** |
| 钻石版 | 125.4 秒 | ~130 秒 | **126 秒** |

**两版都落在基线的 1.3 秒之内**，节点逐项重合：

- 金币版 `0.7 / 17 / 29.9 / 49.2 / 67 / 68.8 / 94.5 / 120.7 / 156.8 / 158`
  对基线 `0.7 / 17 / 30 / 49.4 / 66.4 / 68.2 / 94.4 / 120.8 / 157.9 / 159.3`（最大差 0.6 秒）
- 钻石版 `0.7 / 19 / 25.3 / 45 / 54.6 / 56.5 / 72.9 / 84.3 / 116.9 / 124.7`
  对基线 `0.7 / 18.7 / 25.1 / 45.8 / 53.5 / 55.3 / 71.7 / 84.3 / 116.5 / 124`（最大差 1.2 秒）

两个版本的受力方式不同，最后都归零：

- **金币版**打六只怪花约 4.7 秒（掉落 = 0 时净慢 4.7 秒），那 20 金币又把它抵回来。
- **钻石版**金币本来就过剩（结束时结余 150 以上），20 金币没有用处，所以纯粹是慢 4.7 秒——但那一版的瓶颈是宝石和钻石，挖矿和打守卫的节奏没被动到，落在噪声里。

守卫击杀数不变（低 2 / 中 2 / 高 3，七只全清），宝石与钻石流水不变（`shards {low:2, mid:4, high:10}`、余 10 钻石）。
